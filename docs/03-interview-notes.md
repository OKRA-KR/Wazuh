# 면접 노트 — Wazuh 랩으로 SIEM 공백 메우기

위메이드 인프라보안(블루팀). 자격요건 "보안 로그 분석 경험, SIEM 또는 유사 관제 도구 사용 경험" 공백을 실습으로 메운 것.

> 원칙: **실습 = "직접 세워봤다"이지 운영 경험이 아니다.** 부풀리지 말고 정직하게. 모르는 건 "경험 없습니다, 다만 접근은…"으로.

## 무엇을 했나 (한 문장)

Wazuh SIEM(매니저–인덱서–대시보드)을 docker로 직접 구축하고, 에이전트를 붙여 SSH 브루트포스를 탐지·ATT&CK 매핑까지 확인한 뒤, 오탐을 룰 튜닝으로 조정했다.

## 예상 질문 & 답변

**Q. SIEM 써보셨나요?**
- Wazuh로 직접 구축. 에이전트–매니저–인덱서–대시보드 구조를 손으로 세움.
- SSH 브루트포스를 탐지하고 MITRE ATT&CK(T1110)로 매핑되는 걸 확인.
- 오탐을 `local_rules.xml`로 튜닝 — 레벨 조정·억제.
- 운영 경험은 아니지만 **구조와 탐지 원리는 손으로 익혔다.**

**Q. (킬러) 오탐이 많은데 어떻게 줄이나요?**
- 진단 자동화 도구(OKRA)를 만들 때 오탐을 "성립검증"으로 걸러본 경험이 있다.
- 관제도 같은 문제 — 룰의 조건을 좁히고, 정상 행위는 억제하고, 중요 이벤트는 격상한다.
- 실제로 이 랩에서 브루트포스 빈도 임계값(`frequency`/`timeframe`)이 오탐↔미탐을 가르는 걸 확인했다. 무작정 끄는 게 아니라 미탐 안 나게 균형 잡는 게 핵심.
- **한 줄:** "OKRA는 '이 취약점이 진짜 성립하나'로 노이즈를 걷고, SIEM 룰 튜닝은 '이 로그가 진짜 공격이냐'를 조건으로 걷는다. 도메인만 다르고 사고방식은 같다."

**Q. Security events랑 Configuration Assessment 차이는?**
- 전자는 이벤트 스트림 기반 **실시간 탐지**(룰엔진이 판단).
- 후자는 에이전트가 주기적으로(기본 12h) **자체 진단해 상태를 보고**하는 배치성 점검(CIS 벤치마크).
- 실제로 내 환경은 SSH root 로그인 허용·비밀번호 인증 허용 등이 Fail로 나왔는데, "이 브루트포스가 성공했다면 root로 바로 뚫렸을 것"이라는 리스크가 CA 화면에 수치로 보였다. 탐지와 사전 하드닝을 한 화면에서 엮을 수 있었다.

**Q. 침해사고 대응(IR)은?**
- 운영 IR 경험은 없다(솔직히).
- 다만 진단자로서 공격이 성립하는 경로를 알아서, 로그에서 흔적을 역추적하는 관점은 있다. (예: 알림의 full_log → 어떤 로그 한 줄이 이 경보를 만들었나 추적)

**Q. 트러블슈팅 경험?** (이거 실제로 물으면 강력함)
- 랩 구축 중 컨테이너가 계속 죽었는데, 증상(데몬)→컨테이너→dockerd→WSL VM→호스트 RAM 순으로 레이어를 내려가며 원인을 격리했다.
- 진짜 원인은 컨테이너가 아니라 **호스트 메모리 초과로 WSL VM이 통째로 크래시**한 것. "컨테이너 running ≠ 서비스 정상"을 넘어 "컨테이너가 죽는 것처럼 보여도 원인은 하부 레이어일 수 있다"를 체득했다.

**Q. 게임/블록체인 보안은?**
- 게임사 경험은 없지만 클라이언트 리버싱(frida·dnSpy)이 게임 보안·안티치트와 맞닿아 있다고 본다.
- 블록체인 외부위협 모니터링은 이 랩으로 못 채웠다 → 관심·학습 의지로 정직하게.

## 스크린샷 3장 (준비물)

1. 브루트포스 알림 + ATT&CK 매핑 → "공격이 로그로 남고 SIEM이 상관분석하는 걸 봤다"
2. 커스텀 룰 전/후(Before/After) → "오탐을 룰 튜닝으로 줄였다. 진단 자동화 오탐 제거와 같은 접근"
3. 대시보드 전체 → "매니저-인덱서-대시보드 구조를 직접 세웠다"

## 정직 원칙 (요기요에서 통했던 것)
- 실습은 "직접 세워봤다"까지만. 운영 경험으로 포장 금지.
- 이 랩의 목적은 **"SIEM 안 만져봄" → "구조·탐지·튜닝 손으로 해봄"**으로 바꾸는 것. 그거면 충분.
